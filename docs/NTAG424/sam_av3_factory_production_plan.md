# NTAG 424 DNA 工厂写卡与 SAM AV3 技术方案

## 1. 背景与目标

当前生产流程由卡片工厂执行批量个性化：

1. 工厂先提供待生产卡片的 UID 清单。
   2. 业务侧根据 UID 清单生成每张卡的 Key 0/1/2/3 和完整 NDEF 数据。
   3. 业务侧把密钥、NDEF 和写卡参数交付给工厂。
   4. 工厂使用写卡设备逐卡写入密钥和 NDEF，并开启 SDM。

该流程的主要风险是 Key 0/1/2/3 以明文或可还原形式离开业务侧，工厂软件、操作系统日志、调试工具或备份文件都可能接触到密钥。

引入 SAM AV3 后，目标不是改变 NTAG 424 SDM 的协议，而是：

- 让生产密钥尽量不以明文形式出现在工厂主机和写卡程序中；
  - 在 SAM 内执行或保护 NTAG 424 的 EV2 认证、换钥和受保护写卡命令；
  - 让工厂软件只负责批次调度、UID 匹配、卡片通信和结果上报。

## 2. 角色与边界

| 角色 | 主要职责 | 是否持有生产密钥明文 |
| --- | --- | --- |
| 业务侧密钥服务/HSM | 生成或派生每卡密钥，生成完整 NDEF，维护发行记录 | 是，但仅在受控 HSM/KMS 内 |
| 工厂生产系统 | 读取任务、连接卡片、调用 SAM、写入并校验结果 | 目标是不持有 |
| SAM AV3 | 保存或使用受保护密钥，执行密码运算和安全通道相关操作 | 不向主机导出明文 |
| NTAG 424 DNA | 保存 Key 0~4、File 02 和其他文件，按 SDM 配置动态生成 `e/c` | 芯片内部持有 |
| 服务端 | 保存发行记录，验证读取到的 `e/c` 和计数器 | 持有用于验证的受控密钥或派生能力 |

移动端 App 不使用 SAM AV3。首次碰卡由系统读取可读的 File 02 NDEF 并唤起 App；后续 App 读取 SDM URL 时，只进行普通 NFC 读取和服务端验证。

## 3. 当前流程中的泄漏点

如果业务侧直接向工厂交付如下数据：

```text
UID, Key0, Key1, Key2, Key3, NDEF bytes, FileSettings/SDM offsets
```

则工厂侧至少可以在以下位置看到或复制密钥：

- 任务 CSV/Excel、JSON 或数据库；
  - 写卡软件内存和调试日志；
  - USB、网络传输缓存和临时文件；
  - 操作系统备份、崩溃转储和测试脚本；
  - 人工导入导出或批量重试文件。

即使传输过程使用 HTTPS，密钥到达工厂主机后仍然是明文，HTTPS 只能保护传输链路，不能保护工厂终端本身。

## 4. SAM AV3 主要介入的步骤

SAM AV3 最适合介入工厂实际接触卡片的整个“安全个性化”阶段，而不是只介入某一条写命令：

```text
工厂任务调度
    ↓
读取 UID / 选择对应发行记录
    ↓
SAM 内取得或派生 Key 0/1/2/3
    ↓
AuthenticateEV2First / EV2 Secure Messaging
    ↓
ChangeKey（写入目标 Key 0/1/2/3）
    ↓
WriteData（写入 File 02 NDEF，必要时写 File 03）
    ↓
ChangeFileSettings（配置 SDM、rights、offsets）
    ↓
读回校验并上报结果
```

其中最关键的保护点是：

1. 工厂软件不直接读取生产密钥明文。
   2. `AuthenticateEV2First`、会话密钥派生、CMAC 和加密命令由 SAM 或受保护的密码边界完成。
   3. `ChangeKey` 的新旧密钥材料从 SAM 安全对象进入卡片，不通过普通日志或业务进程传递。
   4. NDEF 和 FileSettings 可以作为非秘密任务参数下发，但必须与 UID 和 profile 严格绑定，防止错卡写入。

## 5. 推荐的密钥交付模式

### 5.1 模式 A：SAM 内预置批次主密钥并按 UID 派生

业务侧不下发每张卡的 Key 0/1/2/3，而是向工厂安全注入设备或 SAM 中写入受控的批次主密钥。工厂软件只提交：

```text
UID
批次号或 profileId
目标 key version
NDEF / SDM 配置参数
```

SAM 按约定的 KDF 派生每卡密钥：

```text
KeyN = KDF(BatchMasterKey, batchId || UID || keyNumber || keyVersion)
```

实际 KDF、输入编码、密钥用途域分离和版本规则必须由业务侧、工厂和 SAM 实现共同固定，并写入发行规范。派生结果不返回给工厂主机。

### 5.2 模式 B：业务侧生成每卡密钥并加密注入 SAM

如果密钥必须由业务侧随机生成，则由 HSM 为每张卡生成 Key 0/1/2/3，再封装成仅目标 SAM 可解封的加密注入包。工厂得到的是密文包：

```text
encryptedKeyPackage = EncryptForSam(uid, keyVersions, key0..key3, profileId)
```

工厂生产软件把密文包提交给 SAM，SAM 解封后将密钥写入内部槽位或直接用于卡片个性化，明文不返回主机。

### 5.3 不推荐模式：HTTPS 下发明文密钥

该模式只能用于受控 Demo 或实验室联调，不适用于正式生产。即使使用短时令牌、TLS 和访问控制，工厂进程仍然可能读取、记录或导出密钥。

## 6. 工厂单卡生产流程

### 6.1 任务准备

业务侧为每个 UID 建立发行记录，至少包含：

- UID 原始字节（固定格式，不使用带冒号的展示字符串参与密码计算）；
  - Key 0/1/2/3 的版本和 HSM/SAM 引用，或加密注入包；
  - File 02 的完整 NDEF 模板；
  - SDM profile：`SDMAccessRights`、`PICCDataOffset`、`SDMMACInputOffset`、`SDMMACOffset` 等；
  - 目标卡片状态和个性化 generation。

File 02 必须包含固定长度的 `e`、`c` 占位符。offset 按 File 02 的完整字节布局计算，包含前置 2-byte NLEN。

### 6.2 卡片个性化

建议每张卡按以下顺序执行，顺序可由具体权限模型调整，但必须记录状态：

1. 读取卡片 UID 和版本，确认与任务 UID 一致。
   2. 选择 NTAG 424 应用并通过 SAM 建立 EV2 安全会话。
   3. 使用旧的管理权限写入目标 Key 1、Key 2、Key 3。
   4. 使用新密钥重新认证并验证版本。
   5. 写入 File 02 NDEF；必要时写入 File 03。
   6. 使用当前 Change 权限写入目标 Key 0（通常最后修改）。
   7. 使用新 Key 0 重新建立会话。
   8. 执行 `ChangeFileSettings` 开启 SDM，保留既定读写权限并写入 offsets/rights。
   9. 重新读取 FileSettings 和 File 02，确认 SDM 已开启、NDEF 长度正确。
   10. 触发一次读取，获取动态 URL，并由服务端验证 `e/c` 和计数器。

每个步骤都应有可重试的状态标记。移卡不会回滚已成功的换钥或写入，不能把一次 NFC 连接当作数据库事务。

### 6.3 SAM 与卡片之间的边界

SAM 保护的是密钥和密码运算；NDEF、FileSettings 和写卡流程控制仍由工厂生产软件编排。生产软件应只能获得：

- 命令成功/失败及状态码；
  - 受控的 KeyVersion、卡片 UID 和生产结果；
  - 必要的非秘密诊断信息。

不得记录：

- Key 0/1/2/3 明文；
  - 会话 ENC/MAC key；
  - 可直接重放的完整安全 APDU；
  - 包含密钥材料的异常堆栈或内存转储。

## 7. 后端需要提供的能力

后端不应只提供一个包含明文密钥的 Excel 文件，至少应提供以下服务：

1. UID 批次登记和去重，生成不可篡改的发行记录。
   2. HSM/KMS 中的密钥生成、派生、版本管理和轮换。
   3. 面向 SAM 的安全注入包或批次派生配置。
   4. 与 UID 绑定的 NDEF 模板、SDM profile 和 offsets。
   5. 工厂设备、SAM 序列号、操作员和批次授权管理。
   6. 生产结果回传、失败重试和审计日志。
   7. SDM URL 验证：使用发行记录中的 Key 1/Key 2（或其 HSM/SAM 引用）验证 `c`、解密 `e` 并检查 `SDMReadCtr` 防重放。

后端可以向工厂下发 NDEF 和配置参数，但应将密钥替换为 SAM 可消费的密文引用或派生任务，不应下发可复制的明文 Key 0/1/2/3。

## 8. SAM AV3 的收益与非目标

### 收益

- 降低工厂主机、写卡 APK/软件和临时文件暴露生产密钥的风险；
  - 将密钥派生、认证和安全消息处理放入专用安全边界；
  - 支持工厂批量写卡，同时保留逐卡 UID 绑定和审计能力；
  - 让密钥轮换、批次撤销和设备授权更容易集中管理。

### 非目标

- SAM 不会自动修复错误的 NDEF、SDM offsets 或 AccessRights；
  - SAM 不会替代服务端对 `e/c` 的验证和计数器防重放；
  - SAM 不会让 File 02 变成不可读，首次系统唤起 App 的需求仍要求其按设计可读；
  - SAM 不负责移动端 App 的普通 SDM URL 读取；
  - SAM 不能挽救已经以明文导出并被复制的历史密钥，旧批次需要单独轮换或报废策略。

## 9. 落地建议

1. 先确定 Key 0/1/2/3 的派生规则、版本规则和 `SDMAccessRights` profile，避免工厂与后端各自解释 key 编号。
   2. 优先采用“业务 HSM + SAM 密文注入”或“批次主密钥在 SAM 内按 UID 派生”，不再交付明文密钥表。
   3. 为工厂软件定义最小接口：提交 UID/taskId，调用 SAM，执行写卡，返回结果。
   4. 在量产前用故障注入验证断电、移卡、重复写卡、错 UID、旧版本密钥和 SAM 拔出等场景。
   5. 将 Demo 的固定密钥、全零传输密钥和明文日志与生产系统完全隔离。

## 10. 结论

在现有“工厂提供 UID、业务侧生成密钥和 NDEF、工厂批量写卡”的流程中，SAM AV3 的核心介入点是工厂执行卡片个性化时的密钥使用环节：从 `AuthenticateEV2First`、`ChangeKey` 到 File 02 写入和 `ChangeFileSettings` 的安全会话。

业务侧仍负责发行策略和密钥生命周期，工厂仍负责生产调度，但生产密钥应由 HSM/SAM 保管或在 SAM 内派生，工厂主机只拿到不可还原的任务数据和操作结果。这样既保留现有批量写卡流程，也显著减少密钥在工厂侧泄漏的机会。
