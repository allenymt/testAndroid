# NTAG 424 DNA Key 0 与 APP 防复制研究

## 结论

Android APP 可以利用 NTAG 424 DNA 做有效的防复制检测，但不能只判断 UID，也不应把长期 AES 密钥直接放进 APK。普通扫码场景推荐使用：

1. 每张卡使用独立（diversified）的应用密钥；
2. NDEF 开启 SDM，输出加密的 UID/读计数器和 SDMMAC；
3. APP 只读取并转交 SDM 数据；
4. 后端/HSM 验证 CMAC、解析卡身份，并原子地检查每张卡的计数器；
5. 对重复或回退的计数器判为重放，对异常大幅跳变、并发首次提交等情况结合业务规则处置。

这能识别普通内存复制和重复播放旧链接，但不是绝对的“不可复制”。如果业务不能接受 SDM 已采集响应被抢先使用、实时中继或单卡硬件模拟的剩余风险，应由专用 APP 通过 `IsoDep` 执行在线挑战-响应认证和安全消息；长期主密钥仍应留在后端/HSM，APP 只中继认证 APDU 或使用受控的安全硬件。

## Key 0 到底是什么

NTAG 424 DNA 的应用中有五个可更改的 AES-128 密钥，编号为 `00h` 到 `04h`。`Key 0` 的官方名称是 `AppMasterKey`；“Key O”是把数字零写成了字母 O，不是官方名称。

需要纠正“Key 1 固定负责 SDM、Key 2~4 固定负责读写”的说法：芯片没有固化这种分工。文件的 Read、Write、ReadWrite、Change 权限，以及 SDM 的 `SDMMetaRead`、`SDMFileRead` 权限，都可以引用 AppKey 0~4 中的某一把密钥。因此 Key 1~4 的实际角色由个性化配置决定。

另外，芯片还有四把由 NXP 写入且不可更改的 PICC 级 `OriginalityKey1..4`。它们用于制造商原始性机制，不属于上述五把客户 AppKey，不能混为一谈。

依据：[NTAG 424 DNA 数据手册](https://www.nxp.com/docs/en/data-sheet/NT4H2421Gx.pdf) §8.2.4、表 14（第 14~15 页），§8.2.3.3~8.2.3.4、表 6~11（第 11~13 页），§8.2.4.5、表 15（第 15 页）。

## Key 0 的权限边界

- `ChangeKey` 要求先用 AppMasterKey（Key 0）认证，并使用 Full 通信模式。Key 0 因而控制五把应用密钥的更新。
- `SetConfiguration` 同样要求 AppMasterKey 认证和 Full 通信模式。
- `ChangeFileSettings` 并非永远要求 Key 0，而是要求该文件当前 `Change` 权限指定的密钥。出厂时三个文件的 Change 权限都指向 Key 0，所以初始配置通常确实要用 Key 0。
- 文件内容的读写权限由各文件访问条件决定，不能简单地把 Key 0 理解为可无条件读写所有内容的“万能超级管理员”。

依据：数据手册 §10.6.1、表 63（第 62~63 页），§10.5.1（第 55~57 页），§10.7.1、表 69/71（第 65~68 页）；[AN12196](https://www.nxp.com/docs/en/application-note/AN12196.pdf) §6.1（第 40 页）。

## SDM 的配置与密钥

SDM 只能在 NDEF 文件 02 上启用，出厂状态为关闭。`ChangeFileSettings` 的 FileOption bit 6 控制 SDM 开关；SDMOptions 决定是否镜像 UID、读计数器、加密文件数据、计数器上限及 ASCII 输出等；SDMAccessRights 决定具体使用哪把 AppKey：

- `SDMMetaReadKey`：用于加密镜像的 PICCData（可包含 UID 和计数器）；
- `SDMFileReadKey`：用于派生 SDM 会话 ENC/MAC 密钥，生成 SDMMAC，并可加密文件数据。

依据：数据手册 §8.2.3.1（第 10 页），§9.3.3~9.3.9（第 36~43 页），§10.7.1、表 69（第 65~67 页）；AN12196 §3.3~3.4（第 8~18 页）。

## 默认密钥与个性化

五把客户 AppKey 的出厂值均为 16 字节 `00h`。NXP 明确建议在个性化时更改全部五把密钥，包括暂时未使用的密钥，而不是只改 Key 0。

“第一步永远先改 Key 0”也不是 NXP 的规则。由于后续 `ChangeKey` 依赖 Key 0 认证，实际流程应由发卡事务设计保证可恢复性；NXP 示例先更改另一把应用密钥，再更改 Key 0。关键要求是离开受控个性化环境前，所有默认密钥均已替换、权限已收紧并完成验证。

依据：数据手册 §8.2.4.2（第 14 页）；AN12196 §5.16、§5.16.1~5.16.2（第 38~39 页）。

## “永久锁死整卡”说法不准确

已核对的 NXP 资料中没有通用的 `Set Lock Byte` / `Freeze` 命令，可在一次操作后永久冻结 NTAG 424 DNA 的所有配置。可确认的不可逆或不可恢复行为是局部的：

- 把某文件的 Change 访问条件设为 `F` 后，后续无法再获得修改该文件设置的权限，相当于永久冻结该文件设置，而不是锁死整卡；
- 启用 LRP 是永久操作；
- 当前 AN12196 说明启用 Random ID 不可逆；
- AppMasterKey 达到配置的失败认证上限而被阻断后，无法恢复。

因此产品方案若要使用“永久锁定”一词，必须准确指出被锁定的是哪项文件设置或配置位，并针对具体芯片版本验证，不能笼统宣称存在全局 Lock Byte。

依据：数据手册表 6（第 11 页）、表 71（第 68 页）、§9（第 20 页）、SetConfiguration 表 50（第 56 页）；AN12196 §6.1~6.2（第 40 页）。

## APP 防复制方案

### 推荐：SDM + 在线后端验证

一次未认证的 NDEF 读取可让芯片生成带 UID/计数器的动态数据及 CMAC。APP 将完整 URL/字段提交后端，后端使用每卡密钥或由 HSM 中主密钥派生的每卡密钥进行验证。

后端至少要保存每张卡已接受的最大计数器（或已见集合），通过原子 compare-and-set 避免并发竞态。策略通常接受“有效且大于已接受值”的计数器，不宜强制必须恰好 `+1`，因为其他手机或攻击性扫描也会推进计数器。启用 SDM 时计数器会复位，重新配置/换卡时必须同步处理服务端状态。

NXP 明确指出：任何人都能采集一个有效 SDM 响应并重放；服务端跟踪每卡 `SDMReadCtr`，拒绝重复或乱序值，是最低要求。因此：

- 复制静态 NDEF/UID 的卡无法生成后续有效 CMAC，容易检测；
- 重放已经被服务端接受的响应可由计数器检测；
- 攻击者预先采集多个未来计数器值，可能抢先使用尚未提交的有效响应；
- 首次提交者是谁无法仅靠 CMAC 判断，实时 relay 也不由 SDM 自动解决；
- 计数器是 24 位，还要设计耗尽、异常跳变、重置和拒绝服务策略。

依据：数据手册 §9.3（第 34~35 页）、§9.3.1~9.3.2（第 35~36 页）；AN12196 §8.1（第 49 页）。

### 更高保证：APP 发起动态双向认证

风险不可接受时，NXP 建议使用挑战-响应双向认证及安全消息，而不是只使用标准 NDEF 的 SDM。Android 可通过 `IsoDep.transceive()` 与标签交换原生 APDU，并让后端/HSM 参与 `AuthenticateEV2`/LRP 会话和后续安全消息计算。这样每次验证都包含验证方的新鲜随机数，不依赖可长期保存的静态 URL。

完全离线也可以做双向认证，但验证端必须持有 AES/LRP 能力和对应卡密钥。把全卡共用的原始密钥写进 APK 风险很高；Android Keystore 的硬件保护能力随设备而异，也不能替代统一受控的 HSM/SAM。若确实要求离线，应优先使用每卡多样化密钥，并评估专用 Secure Element/SAM、设备绑定、密钥轮换及 APP 被攻破后的影响范围。

依据：数据手册 §9.3（第 34 页）；AN12196 §5.16.1（第 38 页）、§8.2（第 50 页）。

## Originality Signature 能做什么

`Read_Sig` 返回 NXP 在制造时对 UID 生成的 56 字节 ECDSA secp224r1 签名，可用 NXP 公钥离线验证。它适合作为“芯片是否由 NXP 制造”的辅助信号和发卡录入检查，但不应作为唯一防复制依据。

NXP 明确说明，该签名用于抵抗把内容批量复制到非 NXP 芯片，并不旨在完全阻止对某一颗芯片的硬件复制或模拟。签名是静态的，也不能证明标签仍附着在原商品上；模拟者如果同时呈现原 UID 与签名，单独验证签名无法发现。

依据：数据手册 §10.10~10.10.1（第 83~84 页）；AN12196 §7.2（第 47~48 页）。

## 建议的落地基线

1. 在受控环境中为每张卡派生不同的 AppKey，替换全部全零默认密钥；主密钥只进入 HSM/SAM。
2. 保护 NDEF 写权限和 Change 权限；按实际需求分配 AppKey，而不是依赖“Key 1 固定做 SDM”的假设。
3. 普通用户触碰采用 SDM：加密 UID + ReadCtr + SDMMAC，后端完成认证和原子防重放。
4. 首次发卡时读取并验证 Originality Signature，将其作为辅助供应链信号。
5. 高价值操作改为专用 APP 的在线动态双向认证；结合账号、设备、时间窗和风险控制，不把 NFC 密码学当作“标签仍在原物品上”的唯一证据。
